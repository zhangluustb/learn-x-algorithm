## Q1: 从用户打开 For You 到看到第一条帖子，系统经历了哪些步骤？每步延迟多少？⭐⭐⭐

**标准答案：**

| 步骤 | 组件 | 延迟 |
|------|------|------|
| 1. gRPC 请求 | 客户端 → Home Mixer | ~1ms |
| 2. Query Hydration | UAS + Strato | ~50ms（并行） |
| 3. 候选获取 | Thunder + Phoenix | ~30ms（并行） |
| 4. 数据补全 | 5 个 Hydrator | ~40ms（并行） |
| 5. 过滤 | 10 个 Filter | ~10ms（顺序） |
| 6. 评分 | 4 个 Scorer | ~100ms（顺序） |
| 7. 选择+后处理 | Selector + VF | ~20ms |
| **总计** | | **~250ms** |

## Q2: 如果要支持 10 倍的用户量，系统需要哪些改动？⭐⭐⭐

**水平扩展：**
- Home Mixer：增加实例数
- Thunder：按用户范围分片（每个实例负责一部分用户）
- Phoenix：增加 GPU 实例

**垂直优化：**
- 模型蒸馏：大模型 → 小模型
- 分级排序：粗排模型 + 精排模型
- 缓存更多 Phoenix 评分结果

---

## Q3: 推荐结果出现了"政治极化"问题，如何从算法层面缓解？⭐⭐⭐

1. 增加负面行为（mute/block/report）的权重
2. 引入"内容多样性"Scorer
3. 减少同话题/同立场的连续推荐
4. 在 Filter 层加入"观点多样性"过滤
5. A/B 测试验证效果

## Q5: 如果 Kafka 丢消息了，Thunder 怎么恢复数据完整性？⭐⭐

1. Thunder 启动时从权威数据库全量加载
2. Kafka 用 at-least-once 语义减少丢失
3. 定期从数据库增量同步补漏
4. 帖子有 TTL，即使丢失也会在 7 天内自然失效
