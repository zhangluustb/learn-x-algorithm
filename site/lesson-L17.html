L17 - 性能优化与工程实践

"在推荐系统中，慢 100ms 意味着流失 1% 的用户——每一毫秒都价值连城。"

📌 本节目标

  1. 理解混合精度推理（bfloat16）的性能收益

  3. 了解 Semaphore 背压与流量控制

正文讲解

1. 混合精度推理（bfloat16）

Phoenix 模型使用 fp32 存储参数、bfloat16 计算推理：

数据类型 内存 计算速度 使用场景
float32 4字节/参数 1x 参数存储、梯度累积
bfloat16 2字节/参数 2-4x 前向传播、矩阵乘法

性能收益： - 内存带宽减半 → 更多数据进 GPU 缓存 - 硬件有专用的 bfloat16 矩阵计算单元（如 TPU bfloat16 MXU） - 推理延迟可降低 40-60%

2. DashMap 无锁并发

Thunder 的 PostStore 用 DashMap 替代标准 HashMap + Mutex：

// DashMap 内部结构（简化）
struct DashMap<K, V> {
    shards: Vec<RwLock<HashMap<K, V>>>,  // N 个分片，通常 N = CPU 核数 * 4
}

分片策略：根据 key 的哈希值分配到不同 shard。不同 shard 的读写完全独立，不会互相阻塞。

线程1: 读 user_123 的帖子 → shard[5].read_lock()
线程2: 写 user_456 的新帖 → shard[12].write_lock()
线程3: 读 user_789 的帖子 → shard[3].read_lock()
                                     ↓
                          三个线程完全并行，零竞争

3. Semaphore 背压控制

struct ThunderServiceImpl {
    request_semaphore: Arc<Semaphore>,  // 如 permits = 1000
}

为什么需要限流？

无限流 有 Semaphore
突发流量导致 OOM 超出容量的请求排队等待
响应时间飙升 保持稳定的响应时间
级联故障 优雅降级

4. Kafka 消费与内存管理

Thunder 的 Kafka 消费策略：

Kafka → 消费 → 过滤过期事件 → 插入 PostStore → 定时裁剪

内存管理要点： - TinyPost（仅 16 字节）用于索引，LightPost 用于全量数据 - 7 天 TTL 自动裁剪，防止无限增长 - VecDeque 从尾部 pop 过期数据，O(1) 操作

5. gRPC + Zstd 压缩

Thunder 和 Home Mixer 之间的 gRPC 通信使用 Zstd 压缩：

压缩算法 压缩率 速度 适用场景
gzip 60-70% 慢 通用
snappy 40-50% 极快 低延迟
zstd 65-75% 快 高压缩率 + 低延迟

Zstd 在推荐系统中是最佳选择——兼顾了压缩率和速度。
